# 🤖 X3AiAnalytics

Conversational intelligence layer over ERP data — **without hallucination**.  
Project developed by **Silvana Siqueira** for **KETHER — Soluções em Inteligência Artificial**.

---

### 🎯 The problem this project solves

Generative artificial intelligence excels at conversation, but is extremely unreliable when handling structured business numbers.

If you ask a generic chatbot *“how much does client X owe me?”*, it might invent a plausible figure, mix up months, confuse revenue with expenses, or confidently provide an answer for something that doesn't even exist.

In an ERP environment, this is unacceptable:
- An incorrect number in a conversation with a client creates a **commercial problem**.
- An incorrect number in a tax report creates a **legal problem**.

💡 **The thesis of this project:** An LLM can converse with the data, but **must never compute the data**. It selects which query to run (executable code), the database returns the exact number, and only then does the LLM draft the response — using exclusively what came from the database.

Question ➔ Scope Classification ➔ Query Planning ➔ Deterministic Execution in Database ➔ Response Composition via JSON

### 🏗️ Architecture

The project is divided into four main layers, following low-coupling principles where dependencies **always point inward**:

- **`X3AiAnalytics.Domain`** — Entities and enumerations. Zero external dependencies.
- **`X3AiAnalytics.Application`** — AI contracts, orchestrator, and response composer.
- **`X3AiAnalytics.Infraestrutura`** — EF Core, SQLite, query catalog, and AI provider implementations.
- **`X3AiAnalytics.Api`** — REST endpoints that perform incoming orchestration.
- **`X3AiAnalytics.Tests`** — xUnit suite covering unit tests, catalog, orchestrator, and HTTP calls.

> 🛠️ **Design Principle:** The Domain is unaware of EF Core, the Application is unaware of SQLite, and the API only consumes contracts. Swapping SQLite for SQL Server or PostgreSQL requires changing only **a single line** in `Program.cs`.

### 🔒 An anti-hallucination guarantee

This mechanism represents the core of the project and relies on three independent pillars:

1. **Explicit out-of-domain refusal:** When the user's question falls outside the ERP domain, no processing LLM is triggered. Refusal is deterministic: the API returns a payload containing `outOfScope: true`, with `data: null` and `queryUsed: null`.
2. **Composition isolated from execution:** The AI model responsible for drafting user-friendly text never has direct access to the database. It exclusively receives the JSON returned by the structured query. There is no technical path for the AI to invent a number, as it possesses no other source of information.
3. **Automated consistency tests:** The analytical test `Ask_StructuredData_ShouldMatch_DirectQueryExecution` compares the textual/structured response generated by the orchestrator against raw query execution from the database. If a single decimal is modified, omitted, or invented, the test suite breaks immediately in CI.

### 🚀 How to run

- **Prerequisites:** .NET 10 SDK installed. The database runs on a local SQLite file, requiring no additional setup.

```bash
# Clone the repository
git clone [https://github.com](https://github.com)
cd X3AiAnalytics

# Build the project
dotnet build

# Run the API
dotnet run --project src/X3AiAnalytics.Api

```

* The API will be available at: `http://localhost:5212`
* Swagger UI for interface testing can be accessed at: `http://localhost:5212/swagger`

#### Endpoints

| Method | Route | Description |
| --- | --- | --- |
| **GET** | `/api/v1/health` | Checks application health status. |
| **GET** | `/api/v1/queries` | Returns the complete query catalog and metadata. |
| **POST** | `/api/v1/queries/{name}/run` | Executes a direct query deterministically (without AI). |
| **POST** | `/api/v1/ask` | Processes natural language user questions. |

#### cURL examples

* **List catalog:**

```bash
curl http://localhost:5212/api/v1/queries

```

* **Execute direct analytical query:**

```bash
curl -X POST http://localhost:5212/api/v1/queries/titulos_vencidos_por_cliente/run \
     -H "Content-Type: application/json" \
     -d "{\"diasMinimosAtraso\":\"30\"}"

```

* **Ask in natural language:**

```bash
curl -X POST http://localhost:5212/api/v1/ask \
     -H "Content-Type: application/json" \
     -d "{\"question\":\"Which customers have accounts overdue for more than 60 days?\"}"

```

*The response from this endpoint returns unified content including: readable text (`resposta`), structured records (`dados`), telemetry tracking (`queryUsed`, `parameters`, `execution time`, `provider`), and the `outOfScope` flag.*

### 🧭 Technical decisions

* **The LLM neither generates nor executes native SQL:** The intelligence provider merely maps question intent to an existing query route within a strict catalog. There is zero risk of SQL Injection or execution outside the auditable action space.
* **Two providers under the same contract:** The system uses `OpenAiProvider` for production environments and `DeterministicAiProvider` as an offline fallback mechanism. This fallback utilizes weighted keyword scoring and a local composer, enabling full testing and demonstrations without cloud infrastructure costs.
* **Mitigated real-world bug (Classification tie):** During development, questions like *“Which customers have accounts overdue for more than 60 days?”* resulted in equal keyword weight between "customer" and "overdue", incorrectly triggering sales revenue queries. The algorithm was corrected to use weighted values (specific business terms weigh 3, generic terms weigh 1). A regression test was created to prevent the bug from recurring.
* **Strict 200-row limit per query:** Prevents context window exhaustion in language models, saves tokens, reduces HTTP latency, and avoids unreadable responses for end users.
* **SQLite for local development:** Zero-config setup to run the ecosystem. The catalog uses fully translatable LINQ expressions, simplifying future migration to other SQL dialects.

#### ⚠️ Known limitations and technical improvements

* **Shared state in composer:** The deterministic provider stores the last processed query state in memory for formatting purposes. In concurrent production environments, this query name should be explicitly propagated via parameters to guarantee thread safety.
* **Post-database overdue day calculation:** The `.Days` aggregation expression based on date difference (`today - dueDate`) caused runtime translation errors in SQLite. To bypass this limitation, the API executes aggregation by fetching the minimum date from the database and calculates the day interval in memory using `.ToListAsync()`.
